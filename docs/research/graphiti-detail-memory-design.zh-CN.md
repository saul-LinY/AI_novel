# Graphiti + Neo4j：故事细节与历程记忆方案

日期：2026-10-14。本文按“辅助上下文记忆、追踪细小线索与实体历程”的目标收敛设计。属于方案设计，尚未部署或进行模型抽取实测。

**建议采用：Graphiti 维护时序关联记忆，Neo4j 直接存储这张图，小说引擎与作者查看界面通过统一服务使用它。** 首期可以直接从现有已提交正文和连续性记录接入，无需先完成全面的物品系统改造。

Neo4j 是 Graphiti 官方支持的主要图数据库后端。配置它后，Graphiti 的图就保存在 Neo4j 中；这里不需要再维护“Graphiti 图”和“Neo4j 图”之间的复制。[官方配置](https://help.getzep.com/graphiti/configuration/neo4j-configuration)

本文先把“同步协同”按以下范围设计：小说提交新回合后更新共享图，多个 Agent 按各自权限读取，作者能查看图和原文证据。多人同时改稿或作者直接编辑事实的协作，可在这套基础上增加版本与修订协议。

**记忆应同时保留当前事实、变化过程与原文证据**

| 记忆层 | 保存内容 | 解决的问题 |
| --- | --- | --- |
| 当前有效事实 | 物品目前由谁持有、人物当前伤势、尚未兑现的承诺 | 下一回合应当遵守什么 |
| 细节事件 | 拿起、交接、遗失、拾回、受伤、承诺、获知、误解、信任转变 | 为什么会变成现在这样，之前经历了什么 |
| 来源 | 正文、回合 ID、逐字引文、故事时间、知情角色 | 记忆是否有根据，谁能使用它 |

以一个假设情节为例：

| 回合 | 事件 | 应保留的细节 |
| --- | --- | --- |
| 3 | 绘梨衣把交流本交给路明非 | 谁交给谁、交接地点、本上已有的折角 |
| 6 | 路明非把交流本遗落在出租车 | 遗落位置与时间，是否有人目击 |
| 8 | 樱拾到交流本 | 新持有者，封面被雨打湿，樱只看见哪部分内容 |
| 10 | 樱把交流本归还绘梨衣 | 流转闭环、归还原因、各人物知道的经过 |

查询“交流本现在在哪里”只需要当前事实；查询“它怎样回到绘梨衣手上”需要事件链；写到她再次翻开本子时，可以召回折角、水痕和相关承诺。人物历程同样记录受伤、救助、欺骗、发现、决定等事件，关系变化则连接相应证据。

**物品归还与反复变化是必须专门处理的情况**

Graphiti 会去重关系事实。所查源码的快速路径在端点与事实文本一致时复用旧关系并追加 Episode 来源；这意味着“A 持有本子 → B 持有本子 → A 再次持有本子”不能仅靠一条持有关系完整表示每次流转。这是源码显示的建模风险，尚未用模型端到端复现。[关系解析源码](https://github.com/getzep/graphiti/blob/9b17e94c16457475f71d5cd2f8045649dd6f170c/graphiti_core/utils/maintenance/edge_operations.py)

因此，每次关键变化应另存一个不可被语义去重吞掉的事件记录，用 `sourceEventId + recordId` 标识，并连接相关实体。事件登记由应用控制稳定 ID 和幂等写入；不能只依靠提示词要求 Graphiti 自动生成不重复的事件节点。

建议区分：

- `Episode`：Graphiti 接收到的来源记录，首期可对应一个已提交回合。
- `DetailEvent`：小说中的一个具体细节变化，一个回合可包含多个。
- `Entity`：人物、具体物品、地点等持续存在的对象。
- 时效关系：由变化形成的某段时间内成立的事实。

`DetailEvent` 是我们增加的领域模型。可以在 Neo4j 中使用应用维护的标签与关系，通过稳定映射连接 Graphiti 实体；其精确检索由记忆服务负责。若要让这些自定义事件也进入 Graphiti 的混合检索，还需适配其节点、关系和索引契约，不是写入任意 Neo4j 节点就自动可检索。

同一个对象保留稳定身份，两个外观相同的本子不合并。重复出现的水痕、特定台词、折角等细节应保留原文，避免多次概括后丢失辨识特征。

**复用现有连续性记录员，减少重复抽取**

当前连续性记录已经包含 `kind/text/quote/characterIds/knownByIds`，并核验引文存在于正文中。[现有契约](/Users/saul/Documents/ChatGPT/AI_novel/src/story-narrative.js:57)

可以按需扩展为以下候选结构，字段未知时不强行填全：

```text
recordId、sourceEventId、turnIndex、storyTime、subEventIndex
kind：transfer / loss / discovery / injury / promise / revelation / detail …
entityRefs：涉及人物、物品、地点的稳定引用
change：发生了什么、之前和之后的明确差异
quote：逐字证据
knownByIds：明确知情的角色
epistemicStatus：事实 / 某人声称 / 某人相信 / 计划
```

普通视觉细节不一定有 before/after；人物说了某句话也不代表话中内容为真。原文引文验证只能证明“这段文字存在”，人物知情范围、实体对应和变化解释还需各自校验。

记录已确认后，保留结构化原件，并给 Graphiti 提供正文与必要记录作为抽取上下文。Graphiti 负责补充语义关联和时效关系；稳定 ID、每次事件 occurrence、已确认状态的精确值仍从原件核对。首次出现的对象先登记候选身份，别名有歧义时保留待定。

**Neo4j 协同方式与更新时机**

建议流程：

```text
本回合正文与记录提交
        ↓
持久化待索引任务，按当前存档/分支排队
        ↓
记忆服务：登记细节事件 + 调用 Graphiti 更新关联
        ↓
Neo4j 保存事件、实体、关系与来源映射
        ↓
更新索引版本 → 通知控制台刷新 → 后续回合按权限召回
```

“实时”定义为每个已提交回合增量更新。抽取存在模型延迟，因此正文提交与图可读之间可能有短暂间隔。UI 显示 `indexedThroughEventId`，区分“故事已保存”和“记忆图已追上”。

若下一回合在入图完成前开始，先补入尚未索引的本地事件和当前状态，再合并较早的图记忆；同一事实按来源去重，近期已提交变化覆盖过期状态。对本轮动作直接相关的旧关系，可在组装上下文时重新核验。不能简单相信检索分数最高的关系就是当前事实。

多个 Agent 使用同一记忆服务，但每个请求携带服务端确定的故事、存档、分支、回合和角色视角。各 Agent 的分析提案先交给主流程裁决，已接受的回合由统一入口写入。首期同分支串行写图，Agent 可以并行读；每轮读固定的故事 head 和可用索引版本，减少分析时所见上下文不一致。

作者可以用 Neo4j Browser 执行查询、查看节点与关系；适合故事阅读的物品流转时间线、人物历程和原句面板需要在现有控制台增加。控制台实时刷新由应用通过现有轮询机制或 SSE 实现，不能假定 Neo4j Browser 中已显示的查询结果会自动刷新。[Neo4j Browser](https://neo4j.com/docs/browser/visual-tour/)

如果以后支持作者修改：通过记忆服务提交可追溯修订，更新关系、来源和必要向量，再通知各读端刷新。直接在 Neo4j 修改字段不会自动改写小说原文或本地存档。改稿、修正抽取错误和修改世界事实应有不同修订语义。

**给写作上下文提供的是一份有边界的记忆包**

每回合先识别当前人物、物品、地点、行动与未解问题，再组合三种召回：

1. 精确召回：相关实体的当前事实、关键未兑现事项。
2. 图关联召回：这些实体参与的历史事件与必要的一至两跳关联；限制关系类型、数量和时间范围。
3. 语义召回：当前动作与描述隐含相关、但没有同名关键词的往事；映射回可信来源。

最终返回：当前事实、必要经历、可呼应的细节、原文证据和不确定之处。先执行角色/分支/时间约束，再按相关性、情节重要性、未解决程度与篇幅预算选择。重要承诺、不可逆伤势等不应仅凭时间衰减被丢弃。

当前 BM25 仍适合补原句与精确词语。Graphiti 可以发现关联来源，再交给现有校验逻辑核对事件、哈希与原文；结构化关系通过单独的 `graphContext` 返回，不冒充原文卡片。[现有检索校验](/Users/saul/Documents/ChatGPT/AI_novel/src/memory/story-memory.js:129)

共享 Neo4j 数据库不意味着各角色共享全部知识。作者视角可以查看完整图；角色输出只使用授权事实。全知摘要和社区摘要也不能直接交给角色。第一阶段可继续用现有角色记忆隔离，先将图检索接到主创与情节分析。

**第一版范围与验收**

先完成一个纵向闭环：已提交回合 → 细节记录 → Graphiti/Neo4j → 按实体查历程 → 下一回合引用原文。只需要必要的稳定实体 ID，不以前置重做完整物品系统为条件。

第一版重点覆盖：

- 物品：交出、归还、遗失、拾回、使用、外观变化。
- 人物：关键经历、受伤、承诺、获知、误解与关系变化。
- 作者查看：实体当前信息、按回合排列的经历、来源原文、索引进度。
- 上下文：与本轮行动有关的有限记忆，保留现有 BM25 与近期事件补齐。

关键测试应包括同一物品反复归还、同名物品、同回合多次转移、角色错误认知、索引落后、重复消费、回退后历史隔离。验收同时检查事件覆盖率、历程顺序、事实准确率、角色泄密、索引延迟和写作实际引用的证据。不能只看 Neo4j 中是否出现了漂亮的关系图。

部署、版本锁定、模型与 embedding 配置等基础风险沿用[可行性研究](/Users/saul/Documents/ChatGPT/AI_novel/docs/research/graphiti-feasibility-2026-10-14.zh-CN.md)。本方案将首期重点放在细节与历程记忆，完整实体状态管理可以按后续实际需要扩展。
