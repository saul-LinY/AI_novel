# 当前流程真实生成耗时测试 · 2026-10-15

结论：两次实测中，最耗时的阶段都是主创裁决（生成结构化提案及返工），分别为 86.9 秒和 88.9 秒。第一轮完成，第二轮在主创提案连续三次校验失败后停止，不能将第二轮计为成功生成。

## 测试方法

- 使用当前工作目录代码、当前 pipeline 配置，以及现有模型 deepseek-v4.1-flash:cloud。
- 从相同正式存档点和相同 Pi 历史会话的副本出发，顺序执行两次相同推荐行动；不清空模型历史，不关闭校验，不改记忆配置。
- 测试行动为“带她的条件下楼”，向地下车库的人转交绘梨衣要药、拿完就走、不被扣留的条件。
- 正式来源回合：c293dcad-ba68-42b7-b944-b734a1f078af。
- 使用真实记忆检索、PiStoryRuntime.generateTurn、appendTurn 和 StoryStore.save。写入仅发生在隔离测试存档。未把测试内容入队至正式后台记忆。
- 计时从检索前开始，第一轮截止隔离存档保存完成；初始化另计，分别约 14 和 15 毫秒。未包含 HTTP、UI 渲染和 turn-job 持久化开销，故是后端核心流程计时。
- 正式故事文件与原有 Pi 会话逐文件 SHA-256 核对，测试前后不变。

## 主创时间花在哪里

第一次：首次提案响应约 73.7 秒，之后的检查及修正约 13.2 秒。主创首次提案引用了不存在的人物 counter-hand，修正一次后通过。

第二次：首次提案响应约 68.9 秒，之后检查及两次修正约 20.1 秒。错误依次为：

1. dramaturgy.valueShift.to 超过 30 字符限制。
2. NPC 不存在：gloved-dispenser。
3. NPC 不存在：gloved-dispenser。达到三次失败上限，停止本轮。

第一轮两次 validateMainProposal 程序检查合计约 4.2 毫秒，第二轮两次该函数检查合计约 2.8 毫秒（不含 SDK schema 校验）。真正可见的等待来自模型首次生成及重新生成提案，不是程序运行校验本身。

两次主创裁决的服务端累计 output token 分别为 19,095 与 22,015，包含模型生成过程的用量，不能视为最终提案或正文的长度。第一轮正文调用的 output token 为 970。首次提案即使不返工也已花约 69～74 秒，因此只消除返工不足以解决主要等待。

## 记忆状态及优化方向

两次检索的全局、环境和两个人物视图均为 ready，无降级、不等待索引。按要求未调整记忆模块。

优先优化主创裁决承担的任务和提案输出要求，并解决导致整份提案返工的字段、人物引用问题；三个子 agent 可以保留。连续性记录在本次成功样本中额外占约 28 秒，但本次仅测试，不修改记录或记忆流程。现有六个历史生成样本中主创裁决也均为最长的单个模型调用，可作为佐证，不能替代本次真实测试。
