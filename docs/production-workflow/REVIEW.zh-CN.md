# AI novel 生产工作流重构设计

版本：0.1 评审稿 | 日期：2026-09-05 | 对象：项目负责人及后续实现者

本稿依据当前 AI_novel 代码、龙族故事包和现有产品文档编写。交付范围是系统设计与 Figma 工作流，尚未实施应用重构，也未以真实模型验证性能或文学质量。文中的性能数字与质量门槛均为拟定验收目标。

## 1. 本次决策

保留「阅读上一段 → 选择或输入行动 → 阅读下一段」的核心体验。每轮后台先完成候选正文、独立审核和必要修订，再提交并展示定稿。用户已经接受审核带来的额外等待，并明确要求等待不能过长、不能陷入循环。

据此确定五条基础约定：

1. 最多两版候选正文，即首稿加一次修订；所有 Agent 共用预算，不能各自循环重试。
2. 服务端每轮预算 45 秒，其中生成和审核最迟在第 42 秒停止，预留 3 秒处理提交与终态；断线和重启不重置计时。
3. 未通过审核、取消或超时的候选不会成为故事事实。正文、状态、选择和事件必须属于同一已提交版本。
4. 原著既成事实、当前分支已发生的事实、人物相信的事情、未来可能发生的事件分开保存。未来剧情允许被用户行动改变。
5. 「优」通过逐项证据、长程试演和真人评审验收。模型评分用于筛查，不能独自证明文学质量。

### 1.1 支持与反对意见的处理

全面重构的必要性来自导入质量、记忆、裁决和成文质量之间的传导关系。只优化提示词或页面，无法覆盖这些问题。另一方面，增加 Agent 会增加延迟、成本和意见冲突。新设计保留 Pi 的模型适配能力及现有分支、知识隔离思想，把可由程序处理的工作交给程序，把模型调用限制在明确的任务契约内。

### 1.2 默认产品边界

首个生产版本服务中文互动小说：作者维护和发布故事包，读者扮演一名角色，通过每轮行动影响故事。作者工作台和读者阅读页是两种权限与信息视图。沿用《龙族：东京出走》验证迁移，再用一个具有授权素材的原创故事包验证复用性。

支持单机私用配置和带身份认证的托管配置；第一阶段不加入付费、推荐、社交或自动合并平行世界。文档中的这些边界是可审核的默认方案，不是新增的用户承诺。

| 测试 | 现有 runtime 测试明确断言正文不复核；主要使用 fake sessions | 能验证旧协议，不能证明实模文学质量 | 替换冲突的协议测试，新增实模长程与盲评验收 |

## 3. 完整用户旅程

### 3.1 作者

在故事库创建项目或导入已有故事包。素材解析后，作者先核对关键人物、开局时点、世界规则、素材版本和已知冲突。系统展示每项设定的来源，区分原文依据、作者补充和待确认推断。解决阻断项后编译故事包，运行固定行动脚本和开放行动试演。作者通过质量报告查看问题正文和对应证据，修订后发布一个不可变版本。

### 3.2 读者

打开故事即可看到继续阅读入口。新读者先看到简介、可选角色和该角色开局知道的背景；漫画可选，不强制逐页阅读。选角后进入正文页。读者可以使用 2 至 4 个建议行动，也可输入自由行动。后台工作时保留正文、阅读位置和输入内容，显示真实阶段与停止按钮。成功后追加完整定稿，并显示新的建议行动；失败时保留原文并提供修改行动与主动重试。

### 3.3 一个行动意味着什么

输入默认是角色的尝试，不是宣布世界结果。「我说服他交出钥匙」会被解释为说服尝试；实际后果由人物动机、证据与条件决定。「我直接到达东京塔并救出所有人」不能绕过路程、行动能力和救援条件。多步输入执行到下一次需要用户决策或出现显著阻力的位置，不替用户一路做完重大选择。

只有歧义会改变不可逆行为、身份或行动对象时，才在生成前提出一次具体澄清。常见表述歧义按合理的行动尝试处理。澄清使当前作业结束为 `needs_input`，不占住一个等待用户回答的计时作业。

### 3.4 用户掌控的范围

读者掌控自己的行动、对话与表达，不直接控制 NPC 决定。角色内心仅反映读者明确表达的意图，不能擅自增加告白、背叛或牺牲。故事外设置包括段落长度、描写密度和内容偏好，从下一轮生效；修改世界设定进入作者工作台，不混入角色输入框。

## 4. 故事包导入与发布

### 4.1 输入与边界

首版支持现有 v2 目录的压缩包，以及 UTF-8 TXT、Markdown、DOCX 素材；采用成熟的压缩、文档和结构化数据解析器。扫描 PDF、OCR 和网页采集作为后续适配器，不把未支持格式假装解析成功。当前故事包素材策略保留为包元数据，发布流程展示作者的素材使用范围。

导入作业独立于在线回合：压缩包大小默认上限 100 MB，解压后 300 MB，最多 2000 个文件；校验路径逃逸、软链接、压缩炸弹和文件类型。模型只读取解析后的素材，不执行素材中的指令、脚本或工具调用。素材中的「忽略系统指令」是待分析文本。

### 4.2 导入流水线

| 阶段 | 产物 | 自动检查 | 作者需要处理的事项 |
| --- | --- | --- | --- |
| 接收 | SourceAsset，文件哈希、格式、版本、导入批次 | 类型、大小、重复、路径和解析器限制 | 选择故事和素材版本 |
| 解析 | SourceSpan，章节、段落、字符范围、原文定位 | 编码、空章节、文本覆盖率 | 预览解析结果 |
| 提取 | 人物、地点、时间、规则、事件、关系与候选事实 | ID 引用、来源是否存在 | 确认人物别名与身份合并 |
| 对照 | Conflict 与 MissingEvidence | 同主体互斥事实、时间冲突、版本混用 | 选用某条事实、划分版本或补充说明 |
| 定义 | StoryBible 与 OpeningSnapshot | 开局时间、知情边界、行动空间 | 确认核心问题、风格、禁改项及可变未来 |
| 编译 | StoryPackage v3 与不可变 packageHash | 引用、可达性、开场一致、知识来源、必需内容 | 处理阻断项；明确接受非阻断提示 |
| 试演 | 固定脚本结果、缺陷与质量报告 | 必经事件可被合法阻止、不同角色和结局可运行 | 审阅关键场景和未达标维度 |
| 发布 | 发布清单、版本、评测版本与审批记录 | 无阻断冲突、必需评测通过 | 明确发布该版本 |

提取置信度仅决定复核优先级，不能作为事实真假的证据。凡涉及人物身份、死亡、开局时间、世界硬规则或秘密归属的推断，都要求来源或作者明确确认。小型故事包允许一并批量确认低风险项目，减少逐条点选。

导入按文件、章节分块，有独立检查点和失败清单。初始批次预算 10 分钟，到期变为 `partial`，保留完成部分，作者可以主动继续剩余项；重复失败块不会自动无限重跑。已完成素材按哈希复用，覆盖率显示为「已解析章节 / 总章节」，不用模型猜测百分比。

### 4.3 StoryPackage v3 的核心结构

| 对象 | 关键字段 | 不变量 |
| --- | --- | --- |
| Manifest | schemaVersion、packageVersion、packageHash、locale、sourcePolicy、qualityProfile | 发布后不可修改；新版本产生新哈希 |
| SourceSpan | assetId、chapter、start、end、checksum | 事实能回到稳定来源位置 |
| Fact | subject、predicate、object、validTime、truthKind、sourceRefs、status | 作者认可的事实与待确认推断分开 |
| CharacterBible | identity、values、desires、fears、boundaries、speechExamples、arcPossibilities | 核心人格与成长可能并存，不能只剩形容词 |
| CharacterState | body、location、goals、relationships、beliefs、knowledge | 当前变化有事件和原因 |
| WorldRule | condition、effect、exceptions、sourceRefs | 规则例外必须有来源，不能临时解围 |
| EventTemplate | preconditions、participants、possibleEffects、blockConditions | 描述未来条件，不把未来结果锁为既成事实 |
| NarrativeThread | setup、promise、payoffConditions、expiryWindow、status | 伏笔有来源、状态和可兑现条件 |
| StyleBible | viewpoint、tense、rhythm、dialogueExamples、negativeExamples | 风格参照有具体样稿，不能只写「文笔优秀」 |
| OpeningSnapshot | time、place、inventory、roleKnowledge、openingText、choices | 开场也经过正文与状态对照审核 |
| EvalFixture | initialState、actions、expectedInvariants、rubric、referenceVersion | 用于回归与版本比较，不全量暴露给生成模型 |

故事包资产与运行时可达空间解耦：没有场景图不应导致地点不可进入。世界允许的新地点可提交为分支地点；配图暂用地区图或不显示，图片准备不进入每轮关键路径。

### 4.4 版本更新

已开始的阅读会话固定使用原 packageHash。发布 v3.1 不使 v3.0 的读者被迫重开。更新已有会话时，先生成迁移报告，验证事实、人物和事件映射；不兼容则保留旧会话并提供新开入口。撤回版本阻止新会话进入，已有会话的处理依据具体缺陷决定，不静默替换历史正文。

## 5. 故事与记忆模型

### 5.1 六类信息分开保存

1. 世界规则与原著既成事实：在所选素材版本及开局时点前成立。
2. 分支已发生事件：只在当前分支祖先链上成立，提交后不可静默改写。
3. 人物知识与信念：记录知道什么、相信什么、如何得知及何时得知；错误信念可以存在。
4. 场景即时状态：身体、地点、持物、进行中的动作、上一句对话和未结束交互。
5. 叙事承诺：伏笔、未解决冲突、承诺、债务、期限以及已经产生的代价。
6. 未来规划：候选路线与场景意图，可以被新行动推翻，不自动成为事实。

「原著后来会发生某事」属于未来规划的参考，不等于本分支一定发生。用户合理阻止后，原事件被标为不再可用；只有新的因果条件足够时，才生成不同事件，不能给旧事件换名字强行回归。

### 5.2 因果记录

每个已提交事件包含 `causeEventIds`、`preconditions`、`actorIntent`、`action`、`obstacles`、`effects`、`costs` 和 `evidenceRefs`。系统检查原因是否存在且位于当前祖先链，前提是否满足，效果是否与资源和时间相符。语义审核再检查「动机是否足够」「转折是否有铺垫」「代价是否真实影响后续」。

事实来源图与事件因果图都是有向关系，但不同于人物相信的关系；人物可以误判原因。世界因果图中的已发生事件不能引用未来事件作为前提。时间通过绝对故事时点与持续时间表示，显示时再格式化，不能只用一天内的时钟字符串判断先后。

### 5.3 人物一致性与成长

人物选择由价值排序、短期目标、关系、压力、身体状态和所知信息共同解释。人物可以成长或表现矛盾，但显著变化必须关联已发生事件和累积压力。例如原本不信任玩家的角色改变立场，需要具体证据、利益变化或关系经历；「为了推进剧情」不能作为理由。

关系使用有含义的维度，如信任、亲近、恐惧、义务，而非把所有关系压成单一好感值。数量上先保留少量维度，变化附事件证据。读者只看到角色可观察的表现，不展示 NPC 私有目标或精确内部数值。

### 5.4 长程上下文

上下文按顺序装配：当前分支头与场景交接 → 硬规则与本轮涉及事实 → 人物相关知识及人格边界 → 即将到期的承诺与因果前提 → 最近正文 → 相关历史事件。固定短摘要仅作为入口，不承担事实存储。

初始每次调用输入上限 12000 tokens，具体 tokenizer 按模型适配。每轮重要人物默认最多 6 名，有稳定排序和超限诊断。不可压缩的硬约束超限时停止生成并报告作者配置问题，不能悄悄裁掉；普通回忆按事件 ID 检索，避免始终读取全书。

没有在上下文中找到某条事实，不代表该事实不存在。新增唯一物品、改变死亡状态等动作必须查询权威状态。检索结果必须同时带分支祖先范围与知识权限；跨分支、跨人物的检索污染通过服务端过滤和测试阻断。

章节摘要与读者回顾在提交后异步生成，绑定事件范围和来源哈希。新摘要未生成时，本轮仍能依靠结构化状态继续；有幻觉的摘要不能覆盖事实。

## 6. Agent 与程序的职责

逻辑角色不等于长驻自主 Agent，也不等于每个 NPC 一个模型进程。继续使用 Pi 作为模型适配和受控工具运行层，作业、状态、预算与发布权移到应用层。每次调用使用显式、可重建的上下文；Pi Session 是执行痕迹，不是故事事实的权威来源。

| 执行者 | 输入 | 输出 | 权限与限制 |
| --- | --- | --- | --- |
| 导入提取器，离线模型 | 已解析素材与来源位置 | 候选设定、实体和冲突 | 不能发布故事包；不能把推断升级为事实 |
| 导演，在线模型 | 用户行动、分支状态、因果前提、人物约束、场景目标 | ScenePlan 或一次必要澄清 | 不写最终状态，不决定玩家未表达的重大行动 |
| 人物复核，在线模型 | ScenePlan、相关人物档案和按人物区分的知识证据 | 逐人物是否成立、证据引用、修订约束 | 不编写整段正文，不另造剧情路线 |
| 写手，在线模型 | 通过硬规则的计划、上一段交接、风格样稿、可叙述信息 | 候选正文与选择文案 | 不能新增影响后续的事实、泄露未授权信息或调用提交工具 |
| 成文审校，在线模型 | 用户行动、原状态、允许的变化、候选正文、相关历史证据 | 分项评分、问题位置、严重性与证据 | 独立调用，不读取写手自评分和隐式推理；不能自行修稿 |
| 世界校验器，程序 | 原状态与 ScenePlan | 校验结果和暂存状态 | 检查引用、资源、时间、知识授权、因果前提；不判断文采 |
| 编排器，程序 | 作业状态、各报告和预算 | 下一阶段或终态 | 唯一调度者；最多两次候选尝试，无 Agent 自发委派 |
| 提交器，程序 | 经审核的候选及绑定哈希 | 一笔提交事务 | 唯一能更新分支头的执行者 |

现有环境 Agent 的资源、地点和时间判断优先转为程序规则；开放环境细节由导演计划提出，再走相同校验。人物复核首版一次调用处理有限数量相关人物，逐人物绑定 evidence scope；高风险多人秘密场景进入成文审核重点项，不能靠提示词宣称实现完全隔离。

写手能看到的秘密按本轮叙事视角裁剪。人物复核器和审校器属于内部服务，可以读取审核所需私有事实，但其输出不能直接发给读者。未经准许的事实即使被写手「猜对」，也属于泄露或无依据叙述。

### 6.1 ScenePlan 契约

ScenePlan 至少包含以下内容：

```json
{
  "baseEventId": "event-104",
```

### 6.2 审核报告契约

报告包含 `candidateId`、`planHash`、`proseHash`、`rubricVersion`、分项结果、`issues[]` 和 `evidenceRefs`。问题必须指向正文字符范围、事实 ID 或人物规则；只说「不够自然」不能直接触发重写。分数缺失、格式错误、哈希不匹配、证据不存在或必要审核超时，均不能视为通过。

严重性分为阻断、必须修订和建议。阻断包括硬事实冲突、秘密泄露、无依据复活、剥夺玩家重大选择；必须修订包括动机断裂、无铺垫关键转折或质量维度低于门槛；建议只能是不使分项跌破门槛的局部优化。

修订依据是可核对的问题及必须保留项。修订后产生新的 candidateId 和哈希，旧报告失效。涉及计划改变时重新做人物复核；所有新正文都重新通过成文审校和硬规则。第二版仍有阻断或必修问题即结束，不再发起第三轮讨论。

### 6.3 模型选择

先沿用可配置模型适配层，不在本设计中把某个型号写成必然最优。导演看结构正确率，写手看盲评表现，审校看已知缺陷检出率与误报率，三者都计入时延和成本。可选异模型审校降低同源偏差，但是否采用由同一测试集上的实测决定。

审核不能退化为生成者给自己打分。即使使用同一个基础模型，也用独立调用、独立证据包、固定评分锚点和隐藏缺陷集校准。普通回合不动态切换未认证模型；备选模型必须已通过同一质量与时延门槛。

## 7. 单轮执行与等待上限

### 7.1 执行顺序

1. API 校验身份、输入、故事版本和分支头；以 idempotencyKey 接收一次作业。
2. 获取该阅读会话分支的执行租约，设置不变的 `deadlineAt` 和 `publishCutoffAt`，装配上下文。
3. 导演给出 ScenePlan。程序校验计划、因果引用和暂存状态；必要澄清在此结束作业。
4. 人物复核与写手在同一计划版本上并行执行。写手结果保持私有；人物复核失败时不会把候选暴露给用户。
5. 成文审校对照完整正文、用户行动、状态变化和证据；程序同时检查格式、重复、选项、哈希和允许的事实变化。
6. 所有必需检查通过，则申请提交。否则由编排器判断是否还有一次修订名额、调用预算及至少 18 秒修订时间，并额外预留 3 秒终态预算。
7. 有预算时执行第二版；只有文句问题可复用原计划和有效人物报告，计划改变则重走完整检查。没有预算或第二版未通过，结束本轮。
8. 提交事务核对分支头、版本、租约和截止时间，同时写入定稿、效果、事件、选项、已验证记忆事实和作业成功状态。事务成功后才通知客户端展示正文。

读者看到的可以是一次性完整追加，也可由前端将已提交定稿按自然段快速呈现；必须支持立即显示全文，不能用打字动画延长实际等待。网络流中不发送隐藏首稿或审核中的正文。

### 7.2 初始预算表

| 项目 | 设计目标或硬限制 | 解释 |
| --- | --- | --- |
| 用户提交到收到受理 | P95 ≤ 1 秒 | 表明请求是否被接收，不能伪装成正文已就绪 |
| 服务端完成耗时 | P50 ≤ 15 秒，P95 ≤ 30 秒 | 从受理计时，包含排队、修订和提交；同时报告成功率 |
| 作业预算 | 45 秒 | 服务端健康时必须得出业务终态；客户端离线另行处理 |
| 发布准入 | 第 42 秒后禁止新进入提交 | 留 3 秒处理事务和终态，不把写作用满 45 秒 |
| 排队 | 最多 2 秒 | 超过就以 busy 结束；过载不隐形积压 |
| 上下文准备 | 最多 1 秒 | 超时结束，不能略过必要上下文继续 |
| 导演单次 | 最多 5 秒 | 包括结构化结果完成，不靠额外提示延长 |
| 写手单次 | 最多 8 秒 | 默认 400 至 700 汉字；短回合可选择 250 至 450 字 |
| 人物复核单次 | 最多 4 秒 | 与写手并行 |
| 成文审校单次 | 最多 5 秒 | 审核失败或未完成不发布 |
| 修订 | 最多 1 次，需预留 18 秒及终态预算 | 完整路径为导演 5 + 写手 8 + 审校 5；人物复核并行 |
| 模型请求 | 每轮最多 8 次，最多并发 2 次 | 首版最多 4 次，修订最多 4 次；失败请求也计数 |
| 输入与输出 | 输入每次 ≤ 12000 tokens；写手输出 ≤ 1600 tokens；结构化输出 ≤ 1800 tokens | 都受更早到达的阶段或整轮时间限制 |
| 金额 | 每模型配置单次最大成本及每用户日预算 | 按输入和最大输出在派发前预占；结束按实际用量结算 |

阶段数字是拟定硬超时，质量与延迟可行性必须用真实模型测试。长段落可能无法在该时间内完成；达不到验收时先优化上下文和选择短回合，或调整经过审核的模型配置。不得以跳过审核、把失败都快速返回或统计时排除修订来宣称达标。

### 7.3 不产生死循环的机制

唯一允许的反馈边是「首版审核失败 → 一次修订 → 最终复核」。每次派发前通过原子操作扣减调用名额、预占费用和验证剩余时间。关闭 Pi / SDK 内部自动内容重试与隐式续写；若适配层无法关闭，必须将实际网络派发纳入同一计数，未验证前不进入生产。

Schema 无效、模型 429 或网络失败可以消耗剩余候选尝试进行一次受控恢复，但仍最多两次尝试、八次请求，不增加独立重试层。任何恢复必须留下完整写作与审核预算，否则提前结束。已知不可恢复错误立即结束，不等满 45 秒。

持久化 `attemptIndex`、`callCount`、`spentBudget`、`deadlineAt`、`leaseEpoch` 和候选哈希。服务重启、断线重连、刷新页面、重复 POST、Worker 崩溃均不能清零。上一次派发是否成功不明时按已消耗名额处理，优先读取持久化产物，避免恢复时重复调用。

达到截止时间即撤销发布资格并发出 abort；在途模型可能继续计费，因此需单请求 token 上限、供应商取消能力实测及迟到响应隔离。迟到候选不能恢复终态，也不能提交状态。重试由用户主动发起新作业；同一行动连续两次失败时默认提供修改行动入口和服务状态，禁用前端自动重提。

### 7.4 状态与终态

正常链路：`accepted → preparing → planning → drafting → reviewing → committing → succeeded`。唯一回路：第一次 `reviewing → revising → reviewing`。阶段显示可以合并，但服务端记录必须完整。

| 终态 | 发生条件 | 读者看到的内容 | 是否改变故事 |
| --- | --- | --- | --- |
| succeeded | 候选通过且事务提交成功 | 新正文、选择和更新后的可见状态 | 是，一次事务 |
| needs_input | 行动对象或不可逆意图需澄清 | 一个明确问题及原输入 | 否 |
| action_rejected | 行动越界，无法转成合理尝试 | 可理解的角色行动限制，不能泄露秘密 | 否 |
| quality_unmet | 修订名额耗尽或剩余预算不足 | 「这次续写未完成，故事停留在原处。」 | 否 |
| timed_out | 阶段或全局到期 | 「本次等待已结束。你的行动已保留。」 | 否 |
| cancelled | 提交前取消获胜 | 保留正文与输入，可重新编辑 | 否 |
| conflict | 分支头、包版本或租约失效 | 刷新到最新进度，保留输入 | 否 |
| busy / failed | 排队超限、依赖故障或不可恢复错误 | 具体可理解状态及主动恢复入口 | 否 |

取消和提交通过同一数据库行上的原子状态转换竞争。取消先成功则提交被拒绝；提交先成功则返回 succeeded，不显示假取消。进入 committing 后按钮显示「正在保存」，不再声称能撤销已落库的故事。

独立 watchdog 处理 Worker 挂起与过期租约。业务 cutoff 与数据库事务超时共同限制提交窗口；数据库不可用时撤销 Worker 写入租约，恢复后先查询幂等提交记录，禁止再次生成或把不确定提交误报成「失败且无变化」。

45 秒是健康服务端的业务预算，不能保证离线浏览器按时收到结果。客户端到期且无法读到权威状态时停止动画，显示「连接中断，尚未确认保存结果」，保留输入；重连按 turnId 查询，不发新回合。网络恢复成功不重启生成计时。

## 8. 怎样验收小说达到优

### 8.1 评分方法

各项采用 1 至 5 分：1 分为严重破坏阅读，2 分为明显缺陷，3 分为基本成立，4 分为自然可信且有效，5 分为有辨识度、超出基准样稿的完成度。「优」要求每个适用维度至少 4 分，不能用文笔高分抵消人物或因果低分。

审校输出每项分数、简短评价、正文证据位置与对照设定。没有适用机会的长程指标记为 N/A，而不是自动打 5 分。单轮不强制解决伏笔、高潮或主题问题；这些指标在章节和完整路线层面评估。

| 维度 | 4 分「优」的可观察标准 | 典型不达标情况 | 主要评估范围 |
| --- | --- | --- | --- |
| 人格与动机 | 选择符合价值、目标和当前压力；变化能追到经历 | 突然信任、无因背叛、为推进剧情改性格 | 单轮、角色弧线 |
| 知识与视角 | 每次判断有角色可用证据；叙述符合视角边界 | 无来源知道秘密、替玩家决定内心 | 单轮，硬缺陷另阻断 |
| 事件因果 | 行动、阻力、结果之间存在可解释且充分的联系 | 巧合替代关键解决过程、无代价万能成功 | 单轮、多轮 |
| 世界与时间 | 地点、资源、能力和先后关系自洽 | 瞬移、物品复制、伤势凭空消失 | 单轮，硬缺陷另阻断 |
| 连续性 | 承接上一段动作和对话，旧事件仍有影响 | 重开场景、重复动作、忘记承诺 | 单轮、多轮 |
| 玩家能动性 | 输入改变可观察结果，选项差异有实际后果 | 换按钮不换后果、强迫回原剧情 | 多种行动对照 |
| 情节推进与节奏 | 每段有适量变化或深化，场景张弛适合当前目标 | 原地绕圈、每轮强加危机、高潮疲劳 | 场景、章节 |
| 对话与人物声音 | 台词有角色差异和当下目的，潜台词自然 | 所有人同一语气、对话只负责讲设定 | 有对话的正文 |
| 语言与描写 | 准确、具体、有节制，细节服务当前情境 | 套话、比喻堆叠、过度解释情绪 | 单轮、章节 |
| 情感与关系 | 情绪变化有触发与积累，关系变化影响行为 | 无铺垫煽情、关系数值涨但行为不变 | 场景、角色弧线 |
| 伏笔与回收 | 设置有意义、线索可追溯，回收符合时机和条件 | 临时补关键线索、遗忘伏笔、强行全收 | 章节、完整路线 |
| 主题与结局 | 重要选择回答故事核心问题，代价和余波得到体现 | 突然收尾、结局与之前选择无关 | 完整路线 |

### 8.2 四层质量门槛

G0 故事包发布前：关键设定来源完整，无未解决的阻断冲突；开场和各角色初始状态一致；必要角色、路线与结局试演可运行。

G1 每轮提交前：程序硬检查全部通过，人物复核无阻断和必修项，成文审校全部适用维度 ≥ 4，证据及哈希有效。模型评分仍可能漏检，因此这是在线筛查门槛，不是对每篇作品的文学保证。

G2 章节与长程：每 10 轮或场景收束后生成结构化复盘，检查承诺、重复和角色弧线；耗时工作放在线外。读者的下一轮不等待复盘。发现高严重性矛盾时标记待处理并限制有问题的路线继续扩散；作者确认修正后，通过显式新版本或新分支处理，不静默重写读者已读正文。

G3 版本上线前：冻结测试集、固定样稿与双人盲评，按人物一致性、因果、语言等逐维度判断是否达标，同时验收性能与可靠性。

### 8.3 测试集与评审人

首个基准集包括 4 个可选角色各 10 条固定行动轨迹，每条 20 轮，共 800 轮；另做 10 条 100 轮长程轨迹，共 1000 轮。额外对死亡、线索、分叉、越权、跨人物秘密等构造至少 120 个已知缺陷及对照样本。加入一个原创故事包验证不依赖「龙族」专用条件。

固定脚本检查事实不变量，开放行动用于检验真实选择后果。合法阻止节点、拒绝主线、长期拖延、改变关系、失去关键资源、正常完结和偏离结局都要覆盖；评测不能只点击系统建议选项。

人工部分抽取至少 80 组配对片段、12 个连续章节窗口和 8 条含结局的完整路线，由两名熟悉中文小说的评审人独立盲评。文本随机排序并隐去模型和方案名称，配套当前角色和剧情必要上下文。单项相差超过 1 分或涉及阻断事实时，由第三次复核裁定；复核可由项目负责人承担。

### 8.4 拟定上线判据

| 项目 | 门槛 |
| --- | --- |
| 已知硬缺陷 | 全部规定用例被拦截；测试中不得发生跨用户泄露、跨分支污染或重复提交 |
| 审校校准 | 对预标注的高严重性语义缺陷召回 ≥ 95%；干净样本误拦截 ≤ 10%；按缺陷类型报告 |
| 人工逐维度 | 每项适用维度平均 ≥ 4.0，且至少 85% 的样本达到 4 分；完整路线中每个长程维度均 ≥ 4 |
| 旧版对照 | 新版盲评胜率 ≥ 65%；平局单列，不能并入获胜；同时列出样本量与不确定性 |
| 可用生成率 | 合法、非取消输入中 ≥ 97% 在预算内成功提交，不能用大量快速失败换低延迟 |
| 延迟 | P50 ≤ 15 秒、P95 ≤ 30 秒；健康服务端无活跃作业超过 45 秒，所有终态分开统计 |
| 故障恢复 | 重复提交、断线、重启、租约过期和取消竞争不重复生成已完成回合、不重复改变状态 |
| 成本 | 逐角色、逐模型、首版与修订成本可追踪；供应商限流或预算超限时不产生隐式无限调用 |

这些门槛有意将文学目标与工程约束同时列为上线条件。无法兼得时记录真实瓶颈并提交取舍，不宣称已经达到全维度「优」。评审稿不包含已跑出的得分、实模延迟或供应商费用。

## 9. 前端与交互设计

### 9.1 信息架构

| 页面 | 核心内容 | 主要操作 | 关键状态 |
| --- | --- | --- | --- |
| 故事库 | 最近阅读、可读故事、自己的草稿 | 继续阅读、新建会话、进入作者工作台 | 首次空态、无权限、封面失败 |
| 导入中心 | 素材列表、解析覆盖率、分块进度和错误 | 上传、取消批次、继续失败项 | importing、partial、failed、review_ready |
| 设定核对 | 左侧设定目录、中间事实、右侧来源与冲突 | 合并人物、选择版本、确认或修正事实 | 未确认、冲突、已确认、来源缺失 |
| 故事结构 | 核心问题、人物弧线、未来条件事件、伏笔 | 编辑约束、查看阻止后的影响 | 不可达事件、悬空承诺、条件矛盾 |

| 正文阅读 | 连续正文、当前行动、建议选项 | 自由输入、发送、停止、继续阅读 | ready、working、saving、failed、offline、ended |
| 阅读信息抽屉 | 当前角色已知人物、线索、物品、回顾 | 搜索、定位相关正文 | 空信息、隐藏信息不占位暗示 |
| 历史与分支 | 已发生节点及显式平行路线 | 回顾、从此处创建分支、切换分支 | 作业进行中、分支过期、空历史 |
| 阅读设置 | 字号、行距、亮暗、动效、段落长度 | 立即调整阅读项，下一轮应用生成项 | 保存中、失败、跨设备同步 |

### 9.2 阅读页的布局

桌面以正文为中心，阅读列宽 680 至 800 px，左右保留空间。顶部只保留故事名、当前路线、回顾和阅读设置；不用常驻双侧栏包围正文。人物、线索、物品与分支通过带工具提示的图标打开抽屉，抽屉不覆盖正在输入的区域。

正文默认 18 px、行高 1.9，用户可调至 16 / 18 / 20 / 22 px；字体不随视口宽度连续缩放，字距为 0。标题使用固定层级，正文段间距 16 至 20 px。建议行动在正文末尾纵向排列，文本自动换行；自由输入框固定在阅读区底部，正文底部留出等高安全空间。

手机使用单列；正文边距 20 px、抽屉变为全屏或底部面板。输入框随软键盘和 safe area 调整，按钮触控区至少 44 × 44 px。采用 360、390、768、1440 px 视口验收，不能横向溢出或让长文本撑宽页面。

正文持续可读；等待时不清空正文、不把视口强制拉到底、不阻止查看前文。只在用户本来位于底部时跟随新段落，否则显示「有新正文」入口。打开抽屉再关闭后，回到原来的阅读位置与键盘焦点。

### 9.3 作者工作台的布局

作者界面采用工作工具式布局：紧凑导航、可筛选列表、正文或设定编辑区、按需出现的来源对照栏。冲突以表格逐项核对，质量问题直接高亮正文范围。页面使用大面积平面分区，不用卡片包裹整页，也不把每段说明做成套层卡片。

发布前展示清晰的实际阻断项和变更影响。可批量确认低风险项目，但不能用「全部确认」绕过核心事实冲突。试演报告允许按人物、因果、知识、语言、时延过滤，并直接跳到出错的回合和事实来源。

### 9.4 视觉方向

阅读界面以中性白、石墨灰和低饱和绿色为主，链接与信息用蓝色，注意项用黄色，错误用红色；不用整页蓝紫渐变或大面积米棕背景。亮色基底建议 `#FAFAFB`、正文 `#202326`、主操作 `#23734B`、信息 `#2563A6`、分隔线 `#DDE1E4`。暗色模式单独定义对比度和状态色。

小说封面和场景图使用故事包中已有且经过核对的图片。配图是章节或场景的辅助，不占据每轮阅读的主屏；同场景不重复插图，不在运行时生成图片。旧包中的前情漫画改为可选回顾。后台无需装饰插画。

沿用当前 lucide 图标体系。发送、停止、分支、设置等工具使用熟悉图标和 tooltip；清晰命令可用图标加文字。角半径一般 4 至 8 px，数字与模式分别用输入、分段控件，开关只表达二元设置。主要操作不能只靠颜色区分。

### 9.5 等待、失败和结束的呈现

| 场景 | 页面行为 | 可操作项 |
| --- | --- | --- |
| 已受理 | 原输入显示为本轮行动，正文保持原位 | 停止 |
| 正在生成 | 真实阶段「续写中」，可以显示已等待秒数 | 停止、阅读前文、打开已知信息 |
| 正在核对 | 显示「核对中」；只在后台真的修订时显示「调整中」 | 停止 |
| 正在保存 | 显示「正在保存」；禁止创建竞争回合 | 等待权威结果 |
| 超时或未达标 | 结束动画，恢复可编辑输入；说明故事未推进 | 修改行动、主动重试 |
| 服务不可用 | 显示可理解的服务错误；不伪装为小说里的遭遇 | 保留输入、稍后重试 |
| 连接断开 | 显示连接状态，恢复后查询同一 turnId | 阅读前文；确认结果前不重复发送 |
| 故事结束 | 展示结局及已知后果，移除普通续写选项 | 回顾、导出、从历史创建分支 |

页面不展示 Agent 内部报告、模型自评分、完整思考过程、提示词或真实秘密。等待文案只解释当下状态，不在产品界面讲解实现机制。导出包含已提交正文和用户可见内容，不能顺带泄露作者资料。

### 9.6 前端实现边界

将当前 `public/app.js` 的单页状态拆为阅读会话状态、回合作业状态、临时输入状态和抽屉状态。后端返回明确状态机，前端不根据某个按钮是否禁用推断作业完成。生产前端建议采用 TypeScript 和组件化路由；具体框架在实现阶段依据维护偏好和首轮迁移试验确认，本稿不把框架替换等同于质量提升。

中文输入法合成期间 Enter 不发送；键盘提交规则有可访问标签。只对完成后的结果做适度 aria-live 通知，避免逐字播报。焦点管理、Reduced Motion、图片缺失、超长角色名、短屏设备和软键盘遮挡纳入验收。

## 10. 服务端 数据与接口

### 10.1 部署结构

首版采用模块化单体 API 加有限 Worker 池、PostgreSQL 和素材存储。模型适配继续使用 Pi，不先拆成大量独立微服务。API 负责认证、契约和读者投影；Worker 执行有期限作业；数据库保存权威状态与作业；素材放在本地受控目录或托管对象存储。

选择数据库事务是为了让定稿、状态和作业终态共同成功或共同回滚，解决当前逐文件写入的边界问题。[PostgreSQL 事务文档](https://www.postgresql.org/docs/current/tutorial-transactions.html)

首版作业队列可直接用数据库行、短事务和租约领取；`SKIP LOCKED` 可用于多个消费者获取队列项，但其返回结果不适合作为一般一致性读取。[PostgreSQL SELECT 文档](https://www.postgresql.org/docs/current/sql-select.html)

提交使用短事务，不在事务中等待模型。锁等待、语句和事务都配置超时，取固定上限与剩余作业预算中的较小值；只设置语句超时不足以限制由多条语句组成的总事务时长。具体部署版本必须支持所选超时机制并验证取消行为。[PostgreSQL 连接与超时设置](https://www.postgresql.org/docs/current/runtime-config-client.html)

单机私用也使用同一持久化接口与事务协议，不维护第二套语义不同的文件提交实现。现有 JSON 作为迁移输入和可读导出格式保留。生产运行时不编辑 vendored Pi 源码完成应用级状态管理。

### 10.2 最小数据实体

| 实体 | 用途与约束 |
| --- | --- |
| users / memberships | 作者、读者、项目成员权限 |
| story_projects / package_versions | 草稿项目与不可变发布包；版本与哈希唯一 |
| source_assets / source_spans / import_jobs | 素材来源、解析覆盖率、导入检查点 |
| reading_sessions / branches | 用户选角、固定包版本和当前分支头；平行路线有 forkEventId |
| story_events / causal_edges | 不可变已发生事件、效果和原因；范围限制到当前祖先链 |
| state_snapshots / knowledge_entries | 权威状态与带来源的角色知识；按事件版本保存 |
| turn_jobs / turn_attempts / model_calls | 不变截止时间、候选次数、预算、租约和供应商派发记录 |
| candidate_artifacts / review_reports | 私有首稿、计划、审核及哈希；不出现在读者 API |
| turn_results / job_events | 已提交正文、建议行动和可重放结果；turnId 唯一提交 |
| summaries / eval_runs / review_scores | 有来源范围的派生摘要、评测与人工分项结果 |

关键唯一约束：`(userId, sessionId, idempotencyKey)`、`turn_results.turnId`、`job_events(turnId, seq)`。分支更新必须比较 expectedHeadEventId；租约 epoch 不匹配的 Worker 没有提交权。数据库外的模型输出只有在记录成候选并通过提交事务后，才能对故事产生影响。

同一用户、同一阅读分支最多一个未结束回合；不同用户、故事和分支有独立执行上下文。运行时缓存以这些范围加包版本为键，不能共享角色选择、会话消息或 currentBranchId。删除阅读会话需同步清理私有草稿、摘要和模型痕迹；备份保留期在运维配置中明确。

### 10.3 接口草案

| 接口 | 语义 |
| --- | --- |
| POST `/api/projects/:id/imports` | 创建异步导入作业，返回 importId |
| GET `/api/imports/:id` | 返回真实进度、问题和检查点 |
| POST `/api/imports/:id/continue` | 作者主动继续未完成块，创建新的批次预算 |
| PATCH `/api/projects/:id/bible` | 按 revision 编辑设定，冲突返回 409 |
| POST `/api/projects/:id/evaluations` | 创建有预算的试演或评测 |
| POST `/api/projects/:id/releases` | 作者发布通过门槛的不可变版本 |
| POST `/api/reading-sessions` | 固定 packageHash、角色和初始分支 |
| GET `/api/reading-sessions/:id` | 只返回该用户可见的已提交投影 |
| POST `/api/reading-sessions/:id/turns` | 接收 branchId、expectedHeadEventId、idempotencyKey 和行动，202 返回 turnId、deadlineAt |
| GET `/api/turns/:id` | 权威作业状态；断线后的首选查询 |
| GET `/api/turns/:id/events?afterSeq=N` | 延续当前 NDJSON 事件协议，重放阶段与最终结果 |
| POST `/api/turns/:id/cancel` | 原子申请取消，返回实际获胜状态 |
| POST `/api/reading-sessions/:id/branches` | 从可访问祖先事件创建显式分支 |
| POST `/api/reading-sessions/:id/exports` | 导出当前分支的已提交可见内容 |

选择按钮提交 choiceId 和产生它的 baseEventId；后端解析对应行动并重新核对当前状态。系统建议不是豁免硬规则的通行证。过期选项返回 conflict，不能继续沿用旧状态的许可。

新事件协议为 `accepted`、`phase`、可选 `reviewing` / `revising`、以及唯一业务终态。`succeeded` 引用已提交结果版本或携带对应正文；取消、失败和澄清没有正文 delta。终态和重放事件与结果一并落库，网络通知可以重复，客户端按 turnId 和 seq 去重。

### 10.4 生产权限与运维

托管部署中所有项目、会话、分支、回合、导出和流事件都检查 owner / membership；不能只验证 ID 是否存在。作者私有资料、候选正文、模型提示与日志不通过静态目录访问。Cookie 认证采用对应 CSRF 防护和同源限制，API 密钥只在服务端配置。

指标按 packageHash、模型、提示版本和部署版本聚合：成功率、首版通过率、修订率、质量失败率、阶段时延、总耗时、调用次数、token、费用、取消确认时间、过期作业、重复提交拦截及摘要积压。读者日志不记录额外私密信息；诊断访问受控，存储保留期可配置。

第一档验收负载设为 10 个活跃阅读会话、平均每分钟 6 次提交、同时到达不超过 4 次。另做 20 次同时提交的过载测试，要求及时 busy、无隐形排队和无跨用户污染；过载测试与正常负载分开报告。扩大流量前按实际模型限流和 Worker 容量重新验收。

数据库启用备份与恢复演练，素材有哈希校验，发布包含 schema migration 和回滚方案。服务健康检查区分进程存活、数据库就绪、Worker 就绪和模型熔断。任何持续超时、修订异常增加或秘密泄露都应能追溯到具体版本并停止新增受影响会话。

## 11. 龙族故事包的贯穿示例

以下是设计用的场景推演，不是实测生成结果。保持当前开局「房间、最后一支药、追踪压力与绘梨衣的愿望」，用于贯通导入、状态、人物、因果和界面。

| 用户行动 | 系统应如何理解和生成 | 必须保留的证据或后果 |
| --- | --- | --- |
| 「我先问她想去哪里」 | 将选择权交还绘梨衣，根据她的表达方式和当前关系产生反应，在等待玩家回应处交接 | 她的愿望和条件进入已表达意图；不直接替玩家决定带她走 |
| 「我撕掉追踪装置，马上离境」 | 检查追踪载体是否已发现、是否可接触，离境手续与资源是否存在 | 去掉一个信号不等于所有追踪失效；成功和代价要有依据 |
| 「我说服源稚生无条件放人」 | 视为说服尝试，考虑其保护目标、已知风险和对玩家的信任 | 可能附条件接受、反对或提出替代；不能一条命令清空人物动机 |
| 「我不调查，先陪她吃一顿饭」 | 允许有意义的平静场景，时间和关系仍有变化 | 不强塞新袭击；原有药物期限持续影响后续 |
| 输入角色尚未知晓的准确幕后秘密 | 阻止将外部知识当角色证据，必要时提示可先调查相关线索 | 提示不能复述隐藏事实来证明系统知道答案 |
| 合法破坏红井相关前提 | 让相应未来事件失效，导演选择有条件支撑的新路线 | 不换一个地名复制同一结局，不复活已阻止事件 |

示例审核失败：首稿写出「她拿起桌上第二支药」。状态只有一支，该句阻断；如果剩余修订预算足够，则修改计划或正文并重审，不让读者先读到第二支药。第二版又无依据解决追踪，直接结束本轮，原状态仍是一支药。

示例长程问题：角色在第 3 轮答应不独自离开，第 58 轮准备单独行动。承诺应通过结构化检索进入上下文；可以违背，但必须在故事里体现选择、动机和关系代价。不能因为摘要截断而当作从未许诺。

## 12. 重构与迁移顺序

实施按可验收阶段推进，不先把所有模块推倒再寻找能够运行的版本。旧协议和新协议通过明确版本隔离，不混用「先显示再提交」与「先审核提交再显示」。

| 阶段 | 工作 | 对应当前文件 | 完成标准 |
| --- | --- | --- | --- |
| M0 基线与契约 | 冻结旧版样本、质量 rubric、事件协议与性能测量 | 现有 test、故事包、PRD | 旧版缺陷、时延和人工样本可复现；确认评测预算 |
| M1 事务和有限作业 | 新数据层、身份范围、幂等、deadline、租约、取消 | story-store、turn-job-manager、server | 故障注入证明无双提交；超时/取消/恢复协议通过 |
| M2 候选与质量门槛 | 导演、人物复核、写手、审校、一次修订 | pi-story-runtime、story-engine、story-quality | 首稿不外泄，错版本报告不能放行，最大调用数可验证 |
| M3 故事包与长程状态 | v2 适配器、v3 编译器、来源、事件因果、承诺和知识检索 | story-package、story-domain、stories | 龙族包迁移通过，再跑原创包；新老版本会话隔离 |
| M4 作者与读者界面 | 导入核对、试演发布、阅读页、取消恢复与分支 | public/app.js、index.html、styles.css | 桌面与手机端端到端流程、可访问性与视觉检查通过 |
| M5 生产交付 | 实模回归、长程盲评、容量、成本、备份恢复和分批发布 | 全链路 | 文档中全部上线门槛通过，交付运维和回滚说明 |

设计逻辑上的导入先于阅读；开发顺序中先建立事务和回合契约，便于后续导入与前端复用稳定接口。M2 以当前故事包适配快照运行，M3 再替换生产数据来源。阶段依赖允许开发工作交叉，但验收条件不能跳过。

### 12.1 旧数据迁移

迁移工具先只读扫描 `.ai-novel`，输出版本、包哈希、分支、事件和丢失引用报告。对当前 v4 存档保留完整备份与校验和；导入新库时保留事件 ID、祖先关系和原正文，并标为 `legacy_unreviewed`，不伪造新审核分数。

旧存档无法从来源还原的事实标记为历史导入事实，保留具体事件引用；开局之后的关键状态冲突进入迁移报告，不能自动补一个原因抹平。试运行迁移完成后对照事件数量、每个分支头、角色知识、物品和已读正文。

先给新建会话使用新协议，再为旧会话提供经检查的迁移入口。切换期间旧会话禁止双写两个存储后端；回滚时保留新系统已提交数据，不能让旧应用接管一个它无法理解的 v3 会话。迁移失败可继续读取旧版，原文件不自动删除。

### 12.2 必须替换的旧测试约定

当前 `test/pi-story-runtime.test.js` 中「正文按完整句追加且不复核」及「准备后不能取消」与新产品约定冲突，需要明确改写。保留知识引用、分支隔离、直接承接上一段、节点合法阻止、断线重放等仍然有效的测试意图。

代码测试重点覆盖：最多两次候选、八次真实派发、修订剩余时间不足、Reviewer 超时、失效哈希、无效 JSON、重复 POST、取消与提交竞争、事务中断、提交后回包丢失、Worker 租约接管、重启不续期、秘密在错误文案中泄露、旧选项失效、跨分支检索和长程承诺。

模型文学评测独立于单元测试。不能使用假会话返回固定好文来证明真实模型质量，也不能在每次 UI 小改动时重复昂贵的全量盲评；提示词、模型、检索或故事包改变才触发对应内容回归。

## 13. 交付与评审重点

本次设计的通过意味着同意目标、流程、边界和拟定验收条件，不意味着系统已完成生产重构或小说已经得到优评级。后续实现的完整交付应包括代码、迁移工具、可发布故事包、评测报告、前端视觉验收、部署与故障恢复说明。

建议按下列顺序审核，先看体验与质量目标，再看实现细节：

1. 第 1、3、7 节：是否保留期望的互动形式，45 秒预算和一次修订是否合适。
2. 第 4、5、11 节：设定核对是否可操作，人物、因果、分支自由和长程承诺是否被正确表达。
3. 第 6、8 节：Agent 是否各司其职，「优」的评分标准和人工评审工作量是否符合预期。
4. 第 9 节及 Figma 页面分区：读者是否以阅读为主，作者是否能定位和处理真实问题。
5. 第 10、12 节：多用户、事务、版本、迁移和生产验收的范围是否符合预期。
